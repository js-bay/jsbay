# Architecture findings

Two issues take priority for dual-engine consumers. A JSC-primary library fails to compile with either QuickJS-family secondary. With the engines in the opposite order, the library builds and accepts scripts on the secondary JSC instance, but a C host cannot drive those scripts to completion. The build matrix and public C observations below apply to the runtime at revision `ad4bb9e`.

## Dual-engine builds

On an Apple target with Zig 0.17.0, the first tag in `-Dbackends` selects the primary engine. The library command was `zig build -Dlibrary-only=true -Dbackends=<pair>`. The suite command was `zig build test-engine -Dbackends=<pair> -Dtest-filter=packed --summary all`.

| Backend pair | Library build | Packed tests |
| --- | --- | --- |
| `quickjs_ng,jsc` | Produced the archive | 20 passed, 1 skipped |
| `quickjs,jsc` | Produced the archive | 19 passed, 2 skipped |
| `jsc,quickjs_ng` | Two compile errors | A targeted secondary-backend evaluation test also failed to compile |
| `jsc,quickjs` | Two compile errors | Suite not run |

Both failing builds reject a QuickJS-family value at two boundaries. The rejection observer calls `api_value.putBorrowed` with a native Promise value, and the Inspector path calls `reportRejection` with native Promise and reason values. Both receivers expect `ActiveEngine.Value`, which is a JSC value pointer in these builds. The dual-engine CI step selects QuickJS-NG as primary. [QuickJS observer](../src/backend/quickjs/exception.zig) · [QuickJS-NG observer](../src/backend/quickjs_ng/exception.zig) · [ABI value storage](../src/abi/api_value.zig) · [Inspector exceptions](../libs/inspector/src/exceptions.zig) · [CI configuration](../.github/workflows/ci.yml)

Keep native value ownership with the instance's backend when passing a borrowed value to an observer. Build all four pairs, then exercise evaluation, rejection observation and handle release on a real secondary instance. Arithmetic alone does not exercise either failing interface.

## Script submission through the public C API

**Accepted work on secondary JSC.** In both `quickjs_ng,jsc` and `quickjs,jsc`, an external C consumer created a JSC instance, read its generation, and called `jsbay_engine_post_script`. Submission returned true. Both `jsbay_engine_run_loop` and `jsbay_engine_attach_loop` returned `JSBAY_UNSUPPORTED`. The completion callback ran zero times before destruction and once with `JSBAY_SUBMISSION_CANCELLED` during destruction. Cancellation during teardown follows the contract. The gap is that the host can enqueue work but has no public driver for that instance. The existing packed submission test reaches normal completion by calling the internal `dispatch.tickInstance`. [Loop entry points](../src/c_api.zig) · [Packed submission test](../src/tests/submission_tests.zig) · [Completion contract](api-contract.md)

Decide whether secondary instances support asynchronous submission. If they do, verify with an external C consumer that an accepted script completes before destruction using a public driver. If they do not, reject the submission immediately and verify that its callback is never invoked.

**Converting a discarded success value executes user code.** A C consumer ran the same script through `jsbay_engine_evaluate` and `jsbay_engine_post_script`. The script reset a counter and returned an object whose `toJSON` incremented it. For each of the three primary backends (QuickJS, QuickJS-NG and JSC), the counter was zero after direct evaluation and one after a single successful submission callback. The queue calls the text evaluator, which converts the result before the queue frees it. The public contract specifies completion status and error text but leaves conversion of success values unspecified. Define whether submission should inspect that value. If it should be discarded, release it directly and retain coverage for script exceptions, debugger notifications and checkpoint order. ## Execution and capability boundaries

- **Execution budgets.** Primary C evaluation keeps an outer execution scope through the checkpoint. Secondary C evaluation calls `execution.end()` before `checkpointInstance`. With no enclosing budget, the checkpoint can establish a new deadline. The scheduler already provides `checkpointInstanceAfterExecution` to retain the original budget. JSC handles Promise reactions inside the VM. Its explicit pending-job hook runs deferred finalizers, so the change in scope alone does not establish that a JSC Promise callback gets extra time. The targeted checkpoint test passed (1/1) in the QuickJS-NG/JSC build and created a primary QuickJS-NG instance. A change to the time available to a secondary Promise callback remains unverified. [C evaluation](../src/c_api.zig) · [Scheduler](../src/runtime/js_scheduler.zig) · [JSC pending jobs](../src/backend/jsc/lifecycle.zig) · [Primary deadline test](../src/tests/runtime_boundary_tests.zig)
- **Module evaluation.** For a secondary instance, `getPtrs` returns the event loop and a zero placeholder for the primary engine's context. Internal `evalModule` and `importModule` select the compile-time backend and pass that context onward. Separate loop lookup from typed context access. Test that each internal entry point either dispatches to the actual backend or returns an explicit unsupported result. The runtime consequence through a public SDK has not been demonstrated. [Instance lookup](../src/runtime/instance_map.zig) · [Module entry points](../src/engine.zig)
- **Capability discovery.** `jsbay_library_capabilities` describes the build primary and `jsbay_engine_capabilities` reports the live instance backend. The latter accepts calls from any thread, holds a control-plane lease, refuses teardown-pending instances, accepts `struct_size >= 4`, preserves that size, and copies at most the supplied bytes. Heap and stack limit plus memory snapshot bits are QuickJS-family only, matching `set_memory_limit` and `get_memory_usage`; interrupt/deadline is absent for Escargot and Hermes, matching their refused interrupt API; explicit bytecode is QuickJS-family primary only, matching typed compile/run rejecting secondary instances; persistent bytecode cache is QuickJS-family primary only when cache support is built, matching evaluation's cache path; CDP debugger is primary only for debugger-capable builds with inspector enabled; Safari Web Inspector is primary JavaScriptCore only. The primary-only restrictions are observable at evaluation, bytecode, and inspector entry points. ## Ownership and directory boundaries

| Finding | Consequence and next check |
| --- | --- |
| [Engine teardown](../src/engine.zig) explicitly releases ABI handles, callbacks, CommonJS references and timers before freeing the VM. | A new resource retaining a JS value needs a matching release in a different directory. Preserve the explicit order and test callback-initiated destruction, pending work and reuse of an instance ID before moving responsibilities. |
| [Thread state allocation](../src/runtime/engine_thread.zig) uses the C allocator and collapses allocation failure into denied entry. The [ABI admission path](../src/abi/value_operation.zig) translates denial for an existing instance into a wrong-thread error. | A caller on the correct thread can receive misleading recovery advice. Carry the failure reason to the ABI and inject failure during first entry to verify the out-of-memory status. |
| The [scheduler](../src/runtime/js_scheduler.zig) looks up the context at the start and end of a backend drain. Each lookup scans the [locked instance registry](../src/runtime/instance_map.zig). | The lookup cost grows with the number of instances. Measure short tasks with 1, 16 and 128 live instances before adding a reverse index. The latency impact is unmeasured. |
| The [Zig package root](../src/root.zig) exports the entire runtime control module, including teardown and budget bookkeeping, alongside curated C ABI declarations. The [architecture guide](architecture.md) lists six local packages, while the [manifest](../build.zig.zon) and [package test target](../build.zig) include nine. | Identify which Zig declarations consumers may rely on before changing exports. Reconcile the package inventory, including the public utility modules, with the build manifest. The existing CommonJS split provides a useful precedent for keeping VM-specific operations in the engine. |

Cover both backend orders and the full public submission path before changing resource ownership or directory layout. Full backend suites, mobile-device runs and scaling measurements remain open.
